# Technical documentation

- Write for a defined audience and task.
- Prefer concise entry points that link to detailed material.
- Keep commands executable and indicate prerequisites, side effects, verification, and rollback.
- Use diagrams for relationships and flows, not decoration.
- Mark status and authority: accepted, verified, inferred, candidate, obsolete.
- Link claims to code, tests, schemas, configuration, ADRs, or official sources.
- Update documentation when contracts, architecture, operations, data model, or developer workflow changes.
